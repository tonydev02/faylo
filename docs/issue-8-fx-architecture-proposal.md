# Faylo Issue #8 — FX reference rates and JPY reporting

**Status:** Final architecture proposal with the approved decisions below. This document does not authorize or include implementation, a production database change, hosted deployment, paid subscription, implementation PR, or user-facing UI change.

**Review base:** Issue #8 and `main` at `6ba3f55e22e9b3d386a90d7e97ea37bb10a5e458` (Issue #7 merged). Main has the transaction and own-account movement foundation; `docs/database.md` says FX conversion is not implemented. The conceptual `docs/data-model.md` FX fields are proposals, not the current database contract. The implemented transaction amount is PostgreSQL `numeric` in major units, validated at the currency scale, and exposed as exact text; do not implement against the conceptual `amount_minor` field names.

The JPY values described here are **reference reporting conversions**, not bank execution values, forecasts, or settlement instructions.

**Recommendation:** Use Frankfurter v2 blended reference rates as the sole external provider in the initial implementation. It covers the required currencies, has dated history, no key or published request quota, and avoids adding a paid dependency. Preserve `Frankfurter blended` as the source label and save the returned effective date and contributor keys; do not describe the blend as a central-bank rate.

**Future fallback, not initial scope:** Currencyapi Free may be evaluated as a fallback in later work. The initial implementation must not integrate it, require or configure its API key, or automatically call it. If Frankfurter has no eligible historical observation, mark the conversion `unavailable`; a transient Frankfurter failure remains retryable `unresolved`. Offer retry or manual override. Never use a current/latest quote for a past transaction date, interpolate, or invent a rate. No paid tier or subscription is proposed.

## 2. Financial architecture and proposed schema

### Invariants

- Keep the original `transactions.amount` and `currency_code` unchanged. Current posted events are immutable; corrections void the original and create a replacement. FX belongs in an owner-scoped sidecar, not in a rewrite of the financial event.
- Store rates as exact PostgreSQL `numeric`, with direction explicitly defined as `1 <original currency> = <rate> JPY`. Do not use JavaScript `number` for rate parsing, multiplication, totals, or rounding. The current app already sends decimal strings and formats money without binary floating point; keep RPC output as text.
- A resolved historical conversion is a frozen per-transaction snapshot. Later provider refreshes do not change a prior report. A manual override requires an explanation, appends a new immutable snapshot revision, and takes precedence over later automatic resolution; prior revisions remain auditable.
- Transfers, card settlements, and balance adjustments are not income/expense reporting conversions. A cross-currency transfer retains the actual sent and received amounts already stored on its two account entries; a reference rate must never replace, equalize, or be presented as either transfer leg.

### Tables to add

**`fx_rate_cache`** — provider observations used to avoid redundant fetches:

- `id`, `user_id`, `base_currency`, `quote_currency`, `rate numeric`, `provider_code`, `effective_on date`, `fetched_at timestamptz`, and minimal provider metadata (for Frankfurter, contributor keys/dates).
- Positive rate and three-letter currency checks; unique provider/pair/effective-date key; owner-scoped RLS and same-owner constraints.
- Cache rows are retrieval aids, not the source of a historical report. Refreshing a cache row must not alter a transaction snapshot.

**`transaction_reporting_fx_snapshots`** — append-only applied conversions:

- `id`, `user_id`, `transaction_id`, `revision`, `status` (`resolved`, `pending_future`, `unavailable`, or `unresolved`), `rate_to_jpy numeric`, `converted_amount_jpy numeric`, `source_kind` (`frankfurter_blended`, `manual`, `identity`, or `unresolved`), provider/source details, `requested_on`, `rate_effective_on`, `fetched_at`, `override_note` (mandatory and nonblank for `manual`), `resolution_reason`, required `idempotency_key`, required `request_fingerprint`, and `created_at`.
- Unique `(user_id, transaction_id, revision)` and `(user_id, transaction_id, idempotency_key)` constraints, plus a composite FK to the same owner's transaction. `idempotency_key` and `request_fingerprint` are non-null. Checks require non-resolved rows to have no rate or converted amount; resolved rows require a positive rate and a whole-yen converted amount. `pending_future` means the economic date has not arrived; `unavailable` means an eligible historical lookup found no rate within the allowed window; `unresolved` covers an absent snapshot or retryable lookup failure. Record the reason. RLS and immutable-update-and-delete protection follow the existing financial audit-table pattern.
- Copy the rate and converted result into the snapshot; do not depend on a mutable cache row to reproduce a report. No new snapshot is required for a provider to refresh an already-resolved transaction.
- **Concurrency and idempotency:** expose owner-checked database RPCs only. Each RPC locks the owning transaction row with `SELECT ... FOR UPDATE`; it first checks for the supplied idempotency key, returns the original result when its normalized request fingerprint matches, and rejects reuse with a different payload. Otherwise, it checks the latest revision and appends `max(revision) + 1` in one database transaction; the unique revision constraint is the final concurrency guard. Transport retries reuse their key; a new deliberate retry after a completed unresolved/unavailable attempt uses a new key. The lock serializes manual and automatic writes: if automatic resolution commits first, a later manual override appends the winning revision; if the manual override commits first, automatic resolution returns it without appending or superseding it. A new deliberate override also uses a new key.
- JPY-native income/expense rows can use an `identity` snapshot with rate one and converted amount equal to the original amount; they do not require an external call. Foreign-currency transactions dated in the future receive `pending_future` and no automatic rate lookup. Missing sidecar rows fail closed; display a future-dated foreign transaction as pending until eligible, otherwise unresolved.

The cache may be upserted as provider data changes; snapshots are append-only. A later explicit override or successful retry of an unresolved/unavailable rate creates a new revision. A correction creates a new transaction and its own snapshot; the voided original and its snapshot remain intact. Automatic resolution never appends over a current manual revision.

## 3. Rate-fetching and caching strategy

1. Use the transaction's stored `occurred_on` in the owner's `Asia/Tokyo` reporting calendar as the economic date. Request the direct `base=<transaction currency>, quote=JPY` historical rate from Frankfurter v2 and request provider expansion for source attribution.
2. Select the latest eligible observation on or before the economic date, with an inclusive seven-calendar-day maximum age: `occurred_on - 7 days <= rate_effective_on <= occurred_on`. Preserve and display the provider's actual `rate_effective_on`. If a successful historical lookup finds no observation in that window, record `unavailable`; do not substitute a future or `/latest` quote.
3. For automatic resolution, return an existing resolved or manual snapshot unchanged. A `pending_future` snapshot is not terminal after its economic date arrives: query a matching cache observation, then Frankfurter v2. If no eligible observation exists, append `unavailable`; a transient fetch failure remains retryable `unresolved`. An explicit manual override is a separate operation and always takes precedence over automatic resolution. Validate response status, requested pair, positive decimal rate, and returned effective date before storing.
4. A foreign-currency transaction whose `occurred_on` is after the current date in `Asia/Tokyo` is not eligible for automatic resolution: store `pending_future` and do not fetch or freeze a historical conversion. It becomes eligible at the start of its economic date in `Asia/Tokyo`. On or after that date, normal on-demand resolution (transaction/report access or an explicit retry) may query Frankfurter v2 using the historical policy above. If no eligible observation is available, append `unavailable`; a transient fetch failure remains retryable `unresolved`. No scheduler is required in the initial design. JPY identity conversions need no external lookup.
5. Make provider calls server-side only. A missing/outage rate must not block posting the user's native-currency transaction. After the idempotent transaction post returns its ID, save the initial `resolved`, `pending_future`, `unavailable`, or `unresolved` snapshot through an owner-checked, idempotent RPC. If that second save fails, the transaction remains posted and the UI treats the absent snapshot as pending-future or unresolved according to its economic-date eligibility; retrying the FX write must not post the transaction again.
6. Use a short bounded timeout and at most one jittered retry for network/5xx/429 failures; respect `Retry-After` where available. Do not retry malformed/unsupported requests. A failed or missing Frankfurter result does not trigger a second provider in the initial implementation.
7. Fetch on demand and coalesce concurrent requests for the same provider/pair/date. Cache historical observations locally; do not add a cron/hosted scheduler. Current account-balance JPY aggregation and JPY investment valuation are deferred to later work.
8. Preserve source and exact decimal tokens. Provider APIs return JSON numeric values; parse the decimal token losslessly (not via `JSON.parse` to JS `number`) and persist it as a decimal string/`numeric`. No amount, merchant, account name, or personal transaction details are sent to a provider—only currency pair and requested date.
## 4. Conversion and rounding rules

- Convert in exact decimal arithmetic: `converted JPY = round(original amount × rate_to_jpy, 0)`. The original amount is in major currency units; its existing currency-scale validation stays authoritative (USD two fraction digits; JPY and VND zero).
- Round each income/expense transaction separately to the nearest whole yen, ties away from zero (`ROUND_HALF_UP`). PostgreSQL documents this behavior for `numeric`; do not round using binary `double precision`. Sum the already-rounded per-transaction JPY snapshots for monthly/category totals so displayed rows reconcile to the chart totals.
- The initial scope converts posted income/expense transactions only. Current account-balance JPY aggregation and JPY investment valuation are deferred; do not fetch latest rates or present converted account/investment values in this work.
- JPY monthly totals include only posted income/expense transactions. Exclude transfers, settlements, and adjustments as current reporting semantics require. Unresolved, unavailable, and pending-future conversions are not zero. A resolved subtotal may be shown only with a clear incomplete label and the count of all included transactions without a resolved conversion.

The source contract uses exact decimals but cannot make a vendor quote more precise than its published rate. Frankfurter also disclaims warranty and notes rates may be revised; the saved transaction snapshot is what makes Faylo's historical result reproducible.

## 5. UI/UX proposal

Follow `docs/design-system.md`: black-first canvas (`#0B0B0C`), neutral charcoal surfaces (`#171717`), off-white text, muted secondary text, and restrained forest/mint accents. Keep most of the view neutral; use readable numeric alignment, explicit labels and accessible status text/icons. Taste (`design-taste-frontend`) was verified installed and readable at `.agents/skills/design-taste-frontend/SKILL.md`; use it before any later UI implementation. No UI was implemented or visually checked for this proposal.

- **Monthly reporting:** retain native-currency totals by currency; never add unlike currencies together. Add distinct JPY-equivalent income and expense summaries/charts based on applied snapshots.
- **Transaction list/detail:** show the original amount/currency as primary. Show the JPY equivalent separately and label it as a reference conversion. Detail reveals rate direction, source, actual effective date, fetched/entered timestamp, and whether it is a manual override. Keep native amounts visible even when conversion is unavailable.
- **Manual override:** provide a clear “Edit reporting rate” action for an eligible transaction. Require a positive decimal rate and a nonblank explanation; record the actual rate-effective date and identify the value as a manual reporting override, not an actual transfer/settlement rate. Preview the rounded JPY result. Saving appends an immutable revision; prior versions remain inspectable. The database RPC enforces the explanation, transaction-row lock, revision uniqueness, idempotency key/fingerprint, and manual-over-automatic precedence.
- **Unresolved conversion:** distinguish a future-dated `pending_future` conversion (not yet eligible for lookup) from an eligible historical conversion marked `unavailable` when no rate meets the seven-day policy; keep transient lookup errors `unresolved` and retryable. Do not show `¥0`, an empty value that looks like zero, or a current-rate estimate as if it were historical. Count every non-resolved included transaction in any incomplete-subtotal disclosure.
- **Account summary:** show native balances only in this issue. Current balance conversion to JPY and investment valuation in JPY are deferred to later work.

## 6. Migration and testing strategy

**Migration plan (future Issue #8 implementation only):**

1. Add the two owner-scoped tables, constraints, indexes, RLS policies and immutable snapshot protections in a new forward-only Supabase migration. Do not change transaction amount columns, account-entry amounts, transfer semantics, or existing immutable-event rules.
2. Backfill existing JPY income/expense transactions with identity snapshots and existing foreign-currency transactions as unresolved, with no provider-derived rate. Do not call a live provider from a schema migration and do not apply a current/latest rate to old rows. An idempotent server-side resolver can later query historical Frankfurter observations under the same economic-date and seven-day rules; future-dated rows remain ineligible until their economic date.
3. Add owner-checked RPCs for recording an initial resolved/pending/unavailable/unresolved snapshot and appending a manual override; enforce transaction-row locking, append-only revisions, and idempotency in the database. Update the existing transaction history and monthly-total contracts/callers to return snapshot metadata and exact text totals. Keep existing native-currency totals and transaction posting/idempotency semantics intact; do not add a parallel compatibility API.
4. Update `docs/data-model.md` and `docs/database.md` to match the implemented schema and explain source/date, unresolved state, rounding, and snapshot lifecycle. Deploy only after owner review, backup/recovery readiness, and explicit approval; none of these changes are applied to production by this proposal.

**Tests for the implementation:**

- Exact decimal arithmetic and serialization; currency-scale boundaries for JPY/VND (zero fractional digits) and USD (two); per-transaction JPY rounding immediately below, at, and above a half-yen boundary, including negative values and ties away from zero.
- Snapshot source/effective-date persistence; Frankfurter response with a prior eligible date; rejection of a future or over-seven-day-old date; pending-future transactions do not call the provider before the economic date and become eligible on that date; no eligible historical rate yields unavailable, while transient failures remain retryable; no latest-rate substitution.
- Manual override requires an explanation, appends a revision, takes precedence over a racing or later automatic resolver, and changes only the JPY reporting result; original amount/currency and account entries remain unchanged; old revision and historical report remain inspectable. Concurrent writers cannot duplicate revisions; retrying the same idempotency key and payload returns the same result, while reusing a key with a different payload is rejected.
- Native-currency monthly totals remain unchanged; JPY totals include posted income/expenses only; any resolved subtotal with pending-future, unavailable, or unresolved included transactions is visibly incomplete and reports the non-resolved count; transfers retain actual sent/received amounts and are excluded from income/expense conversion totals.
- RLS/non-owner denial, cross-owner FK rejection, immutable snapshot revisions, database-level concurrency/idempotency, retry without duplicate transactions, and absence of provider keys in client output.
- Use synthetic test fixtures and stubbed provider responses only—no live finance data or real provider secrets. Run local Supabase/pgTAP, unit tests, and the authenticated browser flow after implementation; review the actual UI at 390px and 1440px per the design system and Taste workflow. No checks were run because this task is proposal-only.

## 7. Approved decisions and scope

- **Provider:** Frankfurter v2 is the only external provider in the initial implementation. Currencyapi remains a documented possible future fallback; do not integrate it or require/configure an API key now.
- **Future-effective transactions:** foreign-currency conversions stay pending until the economic date begins in `Asia/Tokyo`; only then may on-demand historical resolution run. Pending-future is distinct from an unavailable eligible historical rate.
- **Rate selection:** use the latest eligible Frankfurter observation on or before the economic date, no more than seven calendar days old. Preserve and display its actual effective date.
- **Arithmetic:** use exact decimal arithmetic and round each transaction to whole JPY, ties away from zero, before monthly aggregation.
- **Incomplete totals:** show a resolved JPY subtotal only when clearly marked incomplete and accompanied by the number of included transactions without a resolved conversion.
- **Manual overrides:** require an explanation, append an immutable revision, and take precedence over automatic resolution; database locking, uniqueness, and idempotency protect concurrent writes and retries.
- **Backfill:** existing foreign-currency transactions start unresolved. Never use current rates to invent historical conversions.
- **Deferred:** current account-balance JPY aggregation and investment valuation in JPY are later work, not part of this proposal's initial implementation.
- **Preserved invariants:** native transaction money remains unchanged; FX snapshots are owner-scoped and auditable; transaction posting remains idempotent; transfers retain their actual legs and are excluded from income/expense conversion totals.
